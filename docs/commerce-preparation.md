## Data and SQL contract proposed to platform/lead

- `Wallet`: unique `(ownerId, environment, currency)`; customer wallets NGN only; `availableMinor`, `reservedMinor` BIGINT nonnegative; `frozen` boolean plus reason. Never mix provider balances with this table.
- `LedgerAccount`: stable code, environment, currency, normal direction, optional owner. Unique stable owner/environment/currency/account-purpose key. Payment clearing, available liability, reserved liability, sales, returns expense, customer receivable and supplier assets use different accounts.
- `Journal`: unique `(environment, operationId)`; currency; immutable metadata and optional reversal-of journal FK; `postedAt` nullable only inside the creating transaction. Every journal must be finalized before transaction commit.
- `Posting`: journal FK and account FK plus currency, direction `DEBIT|CREDIT`, amount BIGINT `> 0`. Composite FKs `(journalId,currency)` and `(accountId,currency)` prevent a currency bypass. No runtime UPDATE/DELETE privilege. Insert trigger locks the parent journal and rejects any already-posted parent.
- `Quote`: immutable owner/environment/offer-version, retail minor, supplier minor/currency, decimal FX snapshot/source/time, pricing version, entitlement snapshot, expiry and acceptance terms. Quantity is one. `Order.quoteId UNIQUE` is the ultimate one-quote/one-order guarantee.
- `Order`: owner/environment/quote; fulfillment and money states separate; `reservedMinor`, `capturedMinor`, `releasedMinor`, `refundedMinor` BIGINT. CHECK all nonnegative, `captured + released <= reserved`, `refunded <= captured`. Supplier identity/reference stable for the full lifecycle. Optimistic version for operations actions. State writes hold the order lock.
- `IdempotencyRecord`: unique `(ownerId, operation, environment, key)` with canonical request SHA-256 and durable result identity; never expire economic uniqueness while replay remains possible. A mismatched hash is conflict. A different key against a consumed quote returns the existing authorized order rather than buying again.
- `Payment`: unique `(provider, providerAccount, environment, transactionReference)`; expected amount/currency from server intent, credited/reversed aggregate, frozen receivable obligation. Event IDs dedupe inbox delivery; transaction ID dedupes economic credit.
- `Inbox`: unique provider/account/environment/event identity plus authenticated, encrypted payload and digest, processing state/attempts. `Outbox`: unique environment/business event identity, durable claim/lease/attempt state; jobs contain record IDs only. Their economic effects commit with processed marker.

### Deferred constraints and immutability

Use SQL migrations in addition to Prisma. PostgreSQL supports deferred **AFTER ROW** constraint triggers, not deferred row CHECKs. `assert_journal_balanced(journalId)` re-reads the current journal at commit; requires posted status, at least two postings, sum(DEBIT amount) equals sum(CREDIT amount), and matching currency. Attach `DEFERRABLE INITIALLY DEFERRED` triggers to journal INSERT/UPDATE and posting INSERT/UPDATE/DELETE. Attaching only to postings misses an empty journal. Use numeric accumulator semantics for sums so multiple BIGINT postings cannot overflow the aggregate. Runtime role cannot disable triggers, alter tables, truncate, or own financial tables.

An immediate BEFORE UPDATE/DELETE journal trigger rejects changes to any previously finalized journal, including attempts to clear `postedAt`; only draft-to-posted finalization is permitted. An immediate posting insert trigger takes `SELECT ... FOR UPDATE` on its journal before checking draft status. This serializes append versus finalize. All posting UPDATE/DELETE operations fail even while draft; rollback is how a draft is discarded. Reject DELETE journals, including draft journals, so finalization failure must rollback the transaction. A BEFORE TRUNCATE statement trigger is defense in depth; revoked TRUNCATE is the role boundary. Account identity/currency cannot change once referenced.

Wallet materialization must reconcile to posted account movements. Recommended: transactional posting helper updates materialized amounts under the wallet lock, and a deferred wallet reconciliation trigger validates cached amounts equal ledger totals on affected customer accounts at commit. Direct SQL that inserts a balanced journal without a corresponding wallet change must fail, rather than silently introducing drift.

## Transaction sequencing

Use short Prisma interactive SERIALIZABLE transactions. Retry only whole-transaction documented serialization/deadlock conflicts with a bounded attempt count/backoff; no provider, payment, Redis or notification call may enter the transaction. Generate business operation IDs outside retries and reuse them. Lock consistently: wallet/account in stable ID order, quote, order, then payment/event records as applicable; all code paths must agree. Because callbacks begin with an order ID, first obtain the owner/wallet identity without locking, then acquire the same wallet-before-order order and revalidate under locks.

1. Funding: verify exact raw signature outside transaction, validate callback shape/environment/reference/currency/amount against server intent, commit inbox first. Processor reads/verification outside transaction. Consumer locks wallet/payment, validates trusted evidence, inserts one credit journal and marks payment/inbox processed atomically. Callback and poll verification race on the unique payment reference and lock. No credit for partial mismatch.
2. Checkout: validate canonical body/idempotency key; transaction locks owner wallet, quote, existing order; revalidate owner/environment/current publication/version/expiry; reject frozen/insufficient balance. Create order with unique quote, journal available-to-reserved, wallet deltas, accepted quote record, idempotency record and fulfillment outbox atomically. A key conflict re-reads result only after commit; mismatched hash never returns another operation.
3. Dispatch: durable supplier fence/reference/body digest commits before external HTTP. Worker retries inspect the fence. Provider uncertainty leaves money reserved. Graml `DISPATCHING`/`UNKNOWN` cannot authorize another POST. P-AI unknown first looks up the original external reference; safe replay remains gated by verified retention/body/reference guarantees.
4. Completion: wallet then order lock; normalize evidence; delivered final evidence atomically stores encrypted delivery, captures available reservation and advances order. Confirmed failure releases only uncaptured funds. Duplicate events see the existing economic operation. Late queued events do not regress final fulfillment; contradictory final evidence opens a separate review flag.
5. Refund/release: wallet then order lock; immutable operation ID plus current aggregate ceilings under lock. Concurrent new IDs cannot exceed remaining held/refundable balance. Refund is GOOBER purchasing credit, distinct from processor cash refund and supplier asset refund. Goodwill during uncertainty uses explicit loss decision, never falsely labels supplier refund.
6. Reversal/dispute: lock wallet and original payment; unique reversal operation; debit at most currently available customer liability, debit separate receivable for spent difference, credit payment clearing for the reversed total. Freeze spend on unresolved obligation. Never negative spendable balance, delete original credit, release an unrelated held order, or erase the obligation because available is zero. Replay changes nothing. Further funding does not silently remove freeze; resolution policy is explicit.

## State contract

Fulfillment `ACCEPTED → PROCESSING → QUEUED → DELIVERED|FAILED|NEEDS_REVIEW`, with direct PROCESSING-to-final allowed for synchronous fixture outcomes. Review flags preserve delivered history. Supplier attempts `PREPARED → DISPATCHING → ACKNOWLEDGED|UNKNOWN → CLOSED`; UNKNOWN can reconcile but cannot repeat an unprotected POST. Money `RESERVED → CAPTURED|RELEASED`, then CAPTURED to PARTIALLY_REFUNDED/REFUNDED under aggregate ceilings. Timeouts alone authorize neither release nor refund.

## Meaningful evidence to implement

Unit: decimal parser rejects fractions of minor units/exponents/unsafe JSON numbers; exact ceil FX multiplication through integer/rational or decimal arithmetic; `9007199254740993` survives string JSON; malformed/negative amounts fail.

PostgreSQL integration: 20 concurrent checkout submissions with distinct keys against one quote produce one order/journal/outbox; one wallet funded for one item and two independently quoted purchases permits only one reservation. Concurrent payment callback/verification produce one credit. Concurrent refund IDs cannot exceed captured amount. Capture/release races cannot exceed held amount. Forced serializable retry produces no duplicate outbox. Direct SQL commit attempts for empty/unbalanced/cross-currency journals, mutation, finalized append, DELETE/TRUNCATE and cached-wallet drift fail using runtime credentials. Balanced journal + wallet update succeeds. Reconcile every materialized balance to postings.

Recovery integration: kill after checkout commit/before enqueue and rebuild from outbox; kill after supplier accepted/before DB completion and reconcile stable reference without second dispatch; Redis wipe leaves pending database work recoverable; duplicate/out-of-order callback cannot regress delivered/capture twice. Payment dispute after spending freezes once and records receivable with immutable original journals. Restore test preserves journals and decryptable synthetic delivery with dispatch paused.

Browser/API integration: persisted current wallet/order values, body mismatch conflict, quote expiry/tamper rejects, final delivery reveal no-store and owner-only; operations support row reads the same DB order, mode labels visible. External supplier evidence must remain unrun without credentials.
