## Findings

### SEC-001 — High control gap: callback payload stored without secret filtering or encryption

- **Rule:** brief C3 and B7.19; TM-004/TM-007; NEXT-LOG-001 related secret-handling principle.
- **Original location before fix:** `apps/api/src/app.module.ts:42` checked event ID/type/environment only; line 51 persisted `payload: event as Prisma.InputJsonObject`. The original generic route has been replaced by `apps/api/src/webhooks.ts`.
- **Evidence:** every extra property of a correctly signed event reaches ordinary `Inbox.payload`. The model already has `encryptedPayload`, but this route does not use it.
- **Impact:** once this generic callback carries a supplier credential/code or rejected receipt with secrets, that material is stored in plaintext and can reach generic inbox inspection/replay tooling. The present endpoint is isolated fixture-only; no real credentials or live exploitation were observed. High priority is conditional on handling delivery-bearing events, and blocks connecting those events to this generic intake.
- **Fix:** restrict the G1 probe to an exact allowlisted type/schema and construct safe metadata fields explicitly, discarding extra properties. For actual supplier receipts, authenticate first, encrypt sensitive/raw content with order/provider/environment context, and persist only allowlisted identity/status metadata in ordinary JSON. Never serialize the rejected body into exceptions/logs.
- **Verification:** submit a signed synthetic canary in extra `credentials`, `products`, `accounts` and nested fields; assert it is absent from plaintext inbox fields, order summaries, replay responses, logs and client assets. Add an encrypted receipt test when fulfillment callbacks are enabled.
- **Status:** resolved for the implemented local scope. `apps/api/src/webhooks.ts` now uses strict exact fixture probe/payment schemas and allowlisted metadata; P-AI normalized outcomes/unmatched raw receipts use context-bound encrypted envelopes. Independent signed P-AI callback through HTTP on port 3016 returned 202, was processed from its encrypted inbox, and retained no canary in plaintext operational records. Broader public-proxy checks are tracked by the QA acceptance suite.

### SEC-002 — Medium verification blocker: CI does not create its restricted runtime role

- **Location:** `.github/workflows/ci.yml` service initializes only `goober_migrator`; `scripts/configure-ci.mjs:3` rewrites only `DIRECT_DATABASE_URL`; `scripts/infra/permissions.ts:7` grants to `goober_runtime`.
- **Evidence:** local setup generates a random runtime password/URL, but CI does not invoke the native role bootstrap or create that role itself.
- **Impact:** CI cannot apply grants or exercise the real restricted-runtime integration boundary. This is an engineering verification blocker, not a demonstrated remote vulnerability.
- **Fix:** CI-only setup should create `goober_runtime` with its generated password via parameterized/strictly validated bootstrap SQL, with NOSUPERUSER/NOCREATEDB/NOCREATEROLE; apply migrations as migrator and application tests as runtime. Do not solve it by granting the application migrator/superuser credentials.
- **Verification:** run from a fresh CI service/checkout; inspect runtime role flags/table ownership and assert direct SQL cannot mutate finalized financial history or disable triggers.
- **Status:** resolved locally; remote CI remains unrun. `scripts/infra/permissions.ts:7–14` creates the fixed runtime role when missing using its strictly validated generated 64-hex password, with no superuser/create-role/create-db/replication/RLS-bypass capability. Independent fresh database migration/grant setup completed, and the 13 PostgreSQL commerce checks passed, including runtime financial-history protection. The cluster role already existed during this independent run; role creation itself is source-inspected and exercised by clean CI/checkout setup rather than claimed as independently reproduced here.

### SEC-003 — High: normalized supplier failure reason escapes encrypted receipt storage

- **Rule:** brief C3/B7.19; TM-004/TM-007.
- **Original location before fix:** `packages/providers/src/pai.ts:32` copied `failed_reason` into `outcome.reason`; the old `apps/worker/src/processor.ts:33` persisted it directly as `ProviderAttempt.lastError`. Current `processor.ts:17–39` defines safe closed codes; lines 55–57 apply the safe outcome diagnostic.
- **Evidence/impact:** authenticated supplier payloads are encrypted in the inbox, but the consumer subsequently copies arbitrary supplier text into an ordinary diagnostic field. A credential/code contained in a provider failure message becomes plaintext. The present deployment is synthetic/local; no live secret was used or observed.
- **Independent reproduction:** ran `node --env-file=.env --import tsx --input-type=module -e <synthetic-regression>` against loopback PostgreSQL with runtime role. Created a synthetic funded order/attempt, parsed a signed `order.failed` with a unique fake credential in `failed_reason`, persisted its normalized outcome only in encrypted inbox JSON, then called `processInbox`. Result: `canaryInAttemptLastError: true`, inbox `PROCESSED`, order `FAILED`; synthetic order `68b887fb-6601-405c-8a55-5d4ba969966d`. No credentials printed.
- **Fix:** diagnostic columns must contain a closed safe normalized status/error code, never `outcome.reason`. Retain untrusted supplier prose only in the encrypted receipt. Do not use a permissive regex alone to treat supplier strings as safe; codes can still contain secret-bearing tokens.
- **Required regression:** signed callback parser → encrypted inbox → actual worker consumer; assert fake credential absent from plaintext attempts/reviews/orders/outbox, API summaries/replays and logs.
- **Status:** resolved and independently regression-verified 16 October. `apps/worker/src/processor.ts` now uses `outcomeCode` to produce compile-time diagnostics and a closed `OPERATIONAL_CODES` allowlist for exception codes. Untrusted prose remains only in encrypted receipts. Both queued→failed and delivered→contradictory-failed tests passed; independent signed HTTP reproduction now returns 202/PROCESSED and `lastError: supplier-confirmed-failure`, with the canary absent from plaintext records.

### SEC-004 — High: reversal received before success can expire before later funds become spendable

- **Rule:** brief B7.3/9/18; TM-003/TM-004/TM-006.
- **Original location before fix:** old `packages/commerce/src/index.ts:192–198` credited a success whenever `creditedMinor` was zero, but threw `PAYMENT_NOT_CREDITED` on an earlier reversal; the old worker line 146 permanently failed that inbox after six attempts. Current commerce lines 190–210 preserve pending reversal evidence and enforce delayed-credit reversal.
- **Evidence/impact:** gateway event reordering/delay is plausible without an attacker. A conclusive reversal is durably accepted, exhausts automatic retries before delayed success arrives, then success credits spendable purchasing funds even though the reversal is known. This undermines financial evidence ordering and can permit purchases on reversed funding.
- **Independent reproduction:** same local command form and real PostgreSQL runtime role. Created a synthetic intent, inserted an authenticated-equivalent `payment.reversed` inbox first and called `processInbox` six times; then applied delayed `payment.succeeded`. Result: reversal inbox `FAILED`, attempts `6`, wallet available `20000`, `frozen: false`, intent `CREDITED`; synthetic intent `14ba4086-db6c-420e-bae5-565e3bc377a0`.
- **Fix:** atomically persist pending reversal evidence/freeze or reconcile known reversal and delayed success in one locked financial transaction. An already observed reversal must prevent later success from creating spendable credit, including after retry exhaustion/restart. Preserve balanced funding/reversal journals and economic uniqueness; do not erase either event or manufacture negative available funds.
- **Required regression:** out-of-order reversal before success delayed beyond retry budget; replay both event IDs and different event IDs concurrently; assert no reversed funding is spendable, one economic application, durable evidence and correct zero-net journals/obligation treatment.
- **Status:** resolved and independently regression-verified 16 October. `packages/commerce/src/index.ts` now records a unique `PAYMENT_REVERSAL_PENDING` audit event and `REVERSAL_PENDING` intent, freezes spending, and processes any delayed original credit plus its compensating reversal in one locked serializable transaction. The wallet remains frozen for operations review. Independent signed HTTP reversal followed by eight consumer invocations and delayed signed success resulted in available `0`, frozen `true`, intent `REVERSED`, exactly one credit journal and one linked reversal journal.

### SEC-005 — High: pre-hydration native form submission places credentials in URLs

- **Rule:** NEXT-SECRETS-001/NEXT-LOG-001, REACT-AUTH-001 and brief C3/B7.12/19; TM-001/TM-007.
- **Original location:** `apps/web/components/auth-form.tsx:10` rendered an enabled `<form onSubmit={...}>` without an explicit method. Preventing native GET depended entirely on React hydrating and attaching its submit handler.
- **Evidence:** the QA agent's real Chromium journey after sign-out and immediate sign-in interaction produced a native GET to `/sign-in` containing email/password query parameters, observed in the ignored web service log. Only generated synthetic test account credentials were involved. The credential/query value is deliberately omitted from this report.
- **Impact:** a slow/failed hydration or disabled JavaScript allows browser-native form behavior to place a password into browser history, access logs and possible referrer/monitoring sinks before the API's POST and redaction controls apply.
- **Related surface audit:** support and funding forms also rendered before hydration without explicit methods; support text may contain sensitive material despite UI guidance. Operations approval/review forms load after hydration, reducing the original race, but their reason/delivery input should still never fall back to GET. The catalog search's intentional non-secret query behavior is separate.
- **Fix:** explicit POST on mutation forms; disabled SSR fieldset/submit controls until mounted, with handler guard against pre-mount/double submission. Keep credential input out of URLs even if JavaScript never runs or a handler fails. Do not rely on Playwright waiting longer as the security fix.
- **Required regression:** real browser with JavaScript disabled or script delivery blocked sees POST form and disabled credential controls; normal hydrated sign-in still succeeds. Check auth/support form native methods, request URLs and current-run logs using synthetic canaries without printing them. Preserve plaintext credential-free reports/artifacts.
- **Fix review evidence:** `apps/web/components/auth-form.tsx:8–12`, `support.tsx:6`, `wallet.tsx:7` and `operations.tsx:9–10` now use explicit POST/constant actions. `shared.tsx:15` supplies a false SSR hydration state; auth/support/wallet disable the containing fieldset and submit control, and their handlers reject pre-mount/double submissions. Operations forms use POST defensively and are rendered only after client data loads. Catalog search is the only intentionally query-based non-mutating form.
- **Independent rendered evidence:** ReactDOM server render and actual HTTP GETs from the current-source Next.js server at `http://127.0.0.1:3005` each passed for `/sign-in`, `/support`, `/wallet`: HTTP 200, one mutation form, `method="post"`, matching constant action and disabled fieldset. Source-level server rendering used the existing React/tsx toolchain and did not launch another browser/build. Earlier HTTP check during server restart returned connection refused and was retried after readiness; that was not a product failure.
- **Status:** resolved. Independent source and actual SSR checks passed; final lead-run production-build verification passed all six desktop/mobile browser tests, including disabled JavaScript, real sign-out/sign-in and current-log credential canaries. No open high finding remains for local M1.

## Controls visible in source

These observations are static evidence, not runtime test results.
